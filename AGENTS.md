# PaperTodo HarmonyOS Agent Rules

## Formal package is the default

- **User-facing package rule: always deliver a formal signed release package.** Any request to “给我包 / 打包 / 实机测试 / 重新打一个 / 给我安装包 / 发布 / 正式包” means a versioned **release-signed APP** by default. Never hand the user a debug HAP, unsigned HAP/APP, or CI-only developer artifact unless the user explicitly asks for a debug/unsigned developer build.
- When the user asks to build, package, release, or make a “正式包”, use `.github/workflows/harmonyos-package.yml` and produce a versioned **release-signed APP**. Do not substitute an unsigned APP/HAP.
- If application code has changed since the last formal package, increment the installable app version/versionCode as appropriate before producing the next user-facing formal package; packaging-only fixes may rebuild the same not-yet-successfully-delivered application version.
- A formal package is complete only after an AGC release certificate/Profile is created, `hap-sign-tool sign-app`, `hap-sign-tool verify-app`, SHA-256 generation and artifact upload all succeed.
- Required repository secrets are `AGC_SERVICE_ACCOUNT_JSON` and `AGC_APP_ID`. Never print, copy, commit, or ask the user to paste their values. The API client secrets are not needed by the verified signing path.
- Never expose production signing secrets to `pull_request` code. Formal signing may run only from trusted `main` or a reviewed stable tag; ordinary PR validation stays unsigned and must not be presented as a formal package.
- Missing credentials, AGC errors, signing errors, verification errors, missing outputs, or checksum errors must fail the workflow. Never fall back to unsigned output while keeping a formal-package name.
- Formal artifacts and APP filenames must contain the app version, `release`, and `signed`. The ZIP may contain only the verified signed APP, `SHA256SUMS`, and non-secret build metadata.
- **Traditional AGC release certificates use a rolling-slot policy.** `.github/scripts/agc-release-sign.sh` uses the proven keytool-generated one-release P12/CSR path. The private key and temporary P12 exist only for that trusted run. HarmonyOS cross-version updates are anchored by the AGC application `appIdentifier`; a new release certificate may therefore be used for a higher `versionCode`.
- Before creating a new formal release certificate, `.github/scripts/agc-release-slot-maintenance.sh` may reclaim only CI-managed certificates whose names match the versioned `PaperTodo-Release-<semver>-...` pattern. It must delete matching Profile(s) first and the certificate second, preserve at least the newest previous PaperTodo release identity, and never delete unrelated account certificates merely to free quota.
- Keep successful release certificate/Profile pairs until rolling slot maintenance is actually required by the AGC traditional release-certificate limit. Do not immediately delete the just-produced release identity after a successful package.
- Test/diagnostic certificate cleanup may target only explicit test prefixes such as `PaperTodo-Test-*`. Never broad-delete unrelated certificates or Profiles.
- Never commit P12 files, certificates, Profiles, private keys, passwords, JWTs, service-account JSON, or decoded signing material. Signing material may exist only in the runner's temporary directory and must never be uploaded.
- Unsigned builds are allowed only when the user explicitly asks for a debug/unsigned developer build. Call them unsigned test builds, never formal packages.
- After changing application or packaging code, CI must validate the existing Hypium suite before assembly. On a Windows/macOS/device runner this means executing `hvigorw test`; Huawei's Linux Local Test previewer currently stalls after `UnitTestArkTS`, so the Ubuntu workflow must at minimum run the same command under a bounded timeout and require the complete Hypium suite to compile through `UnitTestArkTS` without ArkTS/build errors. Never describe that Linux fallback as assertion execution. Real assertion execution remains a Windows/macOS/device acceptance gate. After changing packaging code, also validate YAML/shell syntax and wait for the trusted remote signing workflow to finish. A local unsigned assembly alone does not satisfy a formal-package request.
